\section{Compiling the Source Code\label{sec:Compiling-the-Source}}

The \textit{build} sub-directory stores a UNIX \textbf{Makefile} that
assembles serial and parallel executable versions with different
compilers. JETSPIN may be compiled on any UNIX platform. From the root
of the repository, invoke this file directly while making \textit{source}
the working directory; there is no need to copy the Makefile. Use

\bigskip{}

\texttt{make -C source -f ../build/Makefile target}

\bigskip{}

where \texttt{target} is one of the options reported in
Table~\ref{Tab:targets}. Object and module files are generated in
\textit{source}, and the resulting \texttt{main.x} executable is placed
in \textit{execute}. For example, the serial GFortran build is produced
with

\bigskip{}

\texttt{make -C source -f ../build/Makefile gfortran}

\bigskip{}

and the corresponding Open MPI build with target
\texttt{gfortran-mpi}. Build products can be removed with target
\texttt{clean} using the same command form.

NVIDIA HPC SDK provides separate CPU-only and OpenACC build targets. On a
module-based installation, first load the SDK and verify that its MPI wrapper
uses NVFORTRAN:

\begin{verbatim}
module purge
module use /opt/nvidia/hpc_sdk/modulefiles
module load nvhpc/24.3
nvfortran --version
mpif90 --showme:command
\end{verbatim}

The serial and MPI CPU-only builds are selected respectively with
\texttt{nvfortran} and \texttt{nvfortran-mpi}. The latter requires
\texttt{mpif90 --showme:command} to report \texttt{nvfortran}.
Neither target enables OpenACC offloading.

The \texttt{nvfortran-openacc} target enables single-GPU OpenACC
offloading. Its default values target compute capability 8.0, including
NVIDIA A30 and A100 GPUs, and the CUDA 12.3 toolkit distributed with HPC SDK
24.3. It also selects the \texttt{nofma} GPU option to preserve the numerical
behaviour of the nearly straight three-point curvature calculation:

\begin{verbatim}
make -C source -f ../build/Makefile nvfortran-openacc
\end{verbatim}

The OpenACC GPU and host-validation targets expose the standard
\texttt{\_OPENACC} preprocessing macro.
Accelerator imports, initialization, Coulomb dispatch, and the dispatch to
the device step are enclosed by this macro. CPU targets preprocess the same sources
without defining it, so accelerator calls are absent from their compiled
translation units rather than being retained as no-op runtime branches.

Another device architecture or installed CUDA toolkit can be selected through
the \texttt{GPUCC} and \texttt{CUDA\_VERSION} Make variables. The
compute capability is passed without the \texttt{cc} prefix; for example:

\begin{verbatim}
make -C source -f ../build/Makefile nvfortran-openacc \
  GPUCC=90 CUDA_VERSION=12.3
\end{verbatim}

HPC SDK 25.5 ships the CUDA 11.8 and 12.9 toolkits, so it is used with
\texttt{CUDA\_VERSION=12.9}; such a build also runs with a driver of the
CUDA 12.3 generation. NVFORTRAN 24.3 at \texttt{-O3} rewrites a division
$x/y$ as $x\cdot(1/y)$ (\texttt{-Mrecip-div}), whereas 25.5, like GFortran,
rounds divisions exactly: the results of the two compilers differ in the
last digits, and trajectories that are sensitive to them separate. An
OpenACC run should be compared with a CPU build of the same compiler
version. NVFORTRAN 24.3 is the reference compiler of the GPU records of
the test cases; 25.5 passes the same checks.

Further Make variables, given on the command line like \texttt{GPUCC},
select the executable name (\texttt{EX}, default \texttt{main.x}) and its
directory (\texttt{BINROOT}, default \textit{execute}), the MPI wrapper
(\texttt{MPIFC}, default \texttt{mpif90}) and the GFortran MPI option
\texttt{MPI\_COMPAT\_FLAG} (default \texttt{-fallow-argument-mismatch};
a GFortran older than version 10 needs \texttt{-Wno-argument-mismatch}),
the NVIDIA compiler (\texttt{NVFORTRAN}), and extra preprocessor flags for
the \texttt{nvfortran*} targets only (\texttt{FPPFLAGS\_EXTRA}, for the
development macros; the oracle and comparison targets below set their
own). Make also takes the variables that have a default (all but
\texttt{EX} and \texttt{BINROOT}) from the environment, so that a
\texttt{CUDA\_VERSION} exported by another tool reaches the build. The
environment variables that control an OpenACC run are described in
Sec.~\ref{sec:Running-GPU}.

Target \texttt{nvfortran-openacc-host} compiles the OpenACC control path
for host execution. It is intended for compiler and numerical validation when
an NVIDIA device is unavailable and is not a GPU performance build. Before a
device run, \texttt{nvidia-smi} and \texttt{nvaccelinfo} should both
confirm that the selected GPU is visible.

Target \texttt{nvfortran-openacc-force-oracle} is a model-independent,
development-only GPU build. At every force evaluation of the device step,
in every configuration that the step supports (Sec.~\ref{sec:Running-GPU}),
it downloads the current stage, evaluates the complete trusted host
equations, and uploads only their derivatives. Integration updates, dynamic
topology, and the tail of the Platen step
(\texttt{accelerator\_platen\_update} and
\texttt{accelerator\_platen\_end\_step}, with the final stress
derivative) stay on the GPU. It enables the single
\texttt{JETSPIN\_DEV\_HOST\_FORCE\_ORACLE} macro.

Target \texttt{nvfortran-openacc-coulomb-oracle} is the narrower diagnostic.
It enables only \texttt{JETSPIN\_DEV\_HOST\_COULOMB\_ORACLE}, transfers the
state required by the direct Coulomb sum, evaluates that sum on the host in
its established order, and uploads the force array. Its semantics are the same
with or without evaporation. Every other force term and the integration
updates remain on the GPU. The two targets are deliberately distinct, and
their per-stage transfers make both unsuitable for production or performance
measurements.

Target \texttt{nvfortran-openacc-host-akima} enables the development-only
\texttt{JETSPIN\_DEV\_HOST\_AKIMA} macro. It retains the historical host
coefficient and interpolation routines while leaving the surrounding OpenACC
refinement lifecycle enabled. Target
\texttt{nvfortran-openacc-compare-akima} enables
\texttt{JETSPIN\_COMPARE\_AKIMA}; it computes the trusted host result followed
by the device result and reports maximum coefficient and interpolated-value
differences for every field. Target
\texttt{nvfortran-openacc-compare-refinement} enables
\texttt{JETSPIN\_COMPARE\_REFINEMENT\_ASSEMBLY} and applies the same
host-then-device comparison to the reconstruction of bead volume,
evaporated volume, mass, and charge that follows the Akima interpolation
(see Sec.~\ref{sec:Dynamic-refinement}). None of these targets is intended
for performance measurements.

On Windows system we advice the user to compile JETSPIN under the
command-line interface Cygwin \cite{racine2000cygwin}. Finally, the
binary executable file can be run in the \textit{execute} sub-directory.
Note that a Fortran compiler that supports the few Fortran 2003 features
used by JETSPIN (Sec.~\ref{sec:Structure}) is necessary in order to
compile it. Further, a Message Passing Interface Implementation should be
also present, if the user wishes to compile JETSPIN in parallel mode. The
Makefile supports GFortran, Intel Fortran and NVIDIA NVFORTRAN; we
recommend GFortran for the CPU builds and NVFORTRAN 24.3 for the OpenACC
build. As Message Passing Interface Implementation, we suggest to use that
provided by the Open MPI Project.
