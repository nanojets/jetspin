\section{Test Case 21: Anchored Dynamic Refinement with Platen Evaporation}

Test Case 21 validates the hybrid OpenACC port of dynamic Akima refinement.
It combines Maxwell rheology, the stochastic Platen integrator,
Yarin evaporation, aerodynamic drag, nozzle insertion, and numerical anchor
beads. The input is stored in
\texttt{examples/input-21/input.dat}.

The initial jet contains 400 elements at a resolution of 0.02 cm and occupies
the interval from the nozzle to 8 cm, while the collector remains at 16 cm.
The free half of the domain permits field-driven stretching. Interior beads
are tagged as anchors every 0.10 cm. These beads are ordinary material points
that remain knots of the old and refined interpolation meshes; no variable
mass or nanoparticle model is enabled.

The refinement target is also 0.10 cm. The reduced charge density limits
sensitivity to the order of the direct Coulomb sum, whereas the increased
external potential makes the short validation reach the refinement threshold.
These choices accelerate a numerical validation and are not proposed as a
reference experimental parameter set. The minimum interval between accepted
remeshes is $5\times10^{-5}$ s, leaving a post-refinement trajectory before
the run ends.

The OpenACC path keeps the Platen stages, pre-generated Gaussian pool,
insertion, and state on the device. Repeated refinement checks return only
three reduction results, in one transfer. At an accepted event the active state is downloaded,
the host walks the mass boundaries and constructs normalized source and
target knots, and Akima coefficient construction and all 11 spline
interpolations execute on the GPU. The GPU then reconstructs the bead and
evaporated volumes from the interpolated radii, rescales them to conserve
the reference volumes, and converts the interpolated mass and charge
densities back to per-bead quantities. The host keeps the anchor bookkeeping
and the final assembly of the mesh, the conservative radius-floor and
evaporation-limit corrections, and the invariant checks, after which the
remeshed state is uploaded once. The
initial allocation reserves 100 additional entries, so the validated event
does not reallocate a mapped array. An additional capacity-growth mode reduces
only this developer reserve to 50 entries. It releases the old persistent
mappings before the host allocation changes, expands the Platen/Coulomb
workspaces, and binds the completed mesh once; the Gaussian pool is not
rebuilt. The same device
Akima kernels are used in both modes.

With GFortran the event occurs at step 7,136 and changes the active count from
413 to 452, ending with 453 elements. With NVFORTRAN 24.3 the CPU event occurs
at step 7,131 and changes 412 elements to 453, ending with 455. The complete
host-force oracle and the native path on one NVIDIA A30 both reproduce the
NVFORTRAN CPU event and topology; their statistics agree with the CPU within
$1.4\times10^{-7}$ and $2.4\times10^{-10}$ relatively.  CPU and GPU read the
same Gaussian pool (Section~\ref{sec:Noise-pool}); what remains is the
different floating-point evaluation order of the device kernels.  Before the persistent-path
fixes of 30 September 2026 the device kept the full charge on the bead being
inserted at the nozzle; the fourth insertion then fell one step earlier, the
pool position was offset, and the native event moved to step 7,125.

All paths start with 79 interior anchors, finish with \texttt{nref=1}, and
preserve anchor positions and fields within the $10^{-12}$ checker tolerance.
Reference and evaporation-volume conservation errors are of order
$10^{-16}$, with no capacity reallocation. The run pre-generates the
$10^{8}$-value Gaussian pool once and uploads it once. A transfer audit
observed, on ordinary steps, one 20-byte topology record and, during
threshold checks, the three reduction results returned in one transfer; at
the Akima event, one full-state download and
upload, one upload of the source and target coordinates, one upload of each
of the 11 source fields and one download of each interpolated field; and the
independent final-shutdown download.

In the capacity-growth mode capacity grows from 450 to 555 entries on all
three paths. Events,
topology, and the whole statistics file are byte-identical to the standard
mode on both builds: the Gaussian pool does not depend on capacity and is
neither rebuilt nor transferred again. A transfer audit again found only the
accepted-event and final full-state downloads, plus one topology/evaporation
rebind and one workspace recreation at the event.

The script \texttt{tests/refinement/run.sh} defaults to GFortran. Its
\texttt{nvfortran}, \texttt{openacc}, and \texttt{force-oracle} arguments run
the corresponding event-level validation paths. Appending
\texttt{capacity-growth} enables the forced-capacity validation.
