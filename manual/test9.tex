\section{Test Case 9: 1,000-bead CPU/GPU performance benchmark\label{sec:Test-Case-9}}

Test Case 9 is a performance-oriented three-dimensional Maxwell simulation
derived from Test Case 7. It initializes 1,000 beads uniformly over the full
16 cm distance from the nozzle to the collector and executes 1,000 integration
steps. Insertion, removal, multiple-step Coulomb summation, and dynamic
refinement are disabled, so the workload remains fixed. The leading bead
starts on the collector; since version 2.0 it is frozen there, like any
bead that reaches the collector, with or without removal (before, it crossed
the collector plane by about $6\times10^{-4}$~cm over the 1,000 steps). The
leading bead of Test Cases 10--12, 15 and 20 also starts on the collector
and is frozen in the same way. With this rule the A30 rows equal the CPU
rows in every printed row; the versioned records were regenerated, and the
normalized differences quoted below predate this change. In version 2.0
Test Cases 9--11 take the common OpenACC device step from the first step,
with 22, 10 and 14 kernel launches per step for RK4, Euler and RK2 (one of
them freezes the beads that reach the collector).

The material, aerodynamic, gravity, and perturbation parameters are retained
from Test Case 7. The orthogonal rotating field is replaced by a constant
axial electric potential. Evaporation is disabled so that the case isolates
the non-evaporative force and integration paths. The case therefore exercises
the direct $O(N^2)$ Coulomb kernel without evaporation coupling or topology
changes.

Test Case 9 is intended for performance comparison rather than as an
additional physical validation baseline. CPU and accelerator runs should be
compared using the terminal value \texttt{Time-integration loop wall time},
which excludes input processing, initial allocation, and accelerator
initialization. Its input is stored in
\texttt{examples/input-9/input.dat}.

After compiling separate CPU and accelerator executables, copy each executable
and \texttt{examples/input-9/input.dat} into a separate run directory. Execute
the two cases sequentially on an otherwise idle system and compare their
\texttt{Time-integration loop wall time} values. The compiler version, GPU
model, GPU compute capability, and build options should accompany every
reported benchmark.

An initial reference measurement with NVFORTRAN 24.3 and one NVIDIA A30
reported 40.659856 s for the CPU executable and 3.785055 s for the OpenACC
executable, corresponding to a speedup of 10.742. Both runs retained exactly
1,000 beads and agreed within the numerical regression tolerances. These
timings are indicative and should be remeasured on each target system.

The most recent timings were measured in October 2026 with NVFORTRAN 24.3,
the process bound to the NUMA node of its GPU, and the present
three-dimensional Coulomb kernel, which spreads the sources of each target
bead over the vector lanes of one gang and no longer uploads array
descriptors at every call. The Test Case 9 loop took 0.508 s on one A30,
against 2.121 s with the previous kernel on the same node and 24.94 s for
the NVFORTRAN CPU executable. Test Cases 10, 11 and 12 took 0.122, 0.223 and
0.354 s, against 0.589, 1.078 and 1.659 s with the previous kernel; Test
Cases 9--14 run 4.2 to 4.8 times faster than with it. Only the summation
order changes, and the outputs still passed their recorded comparisons. The
other timings of this section and of Test Cases 10--14 were measured with
earlier kernels.

An optional internal subroutine profiler is enabled at run time with
\texttt{JETSPIN\_PROFILE=1 ./main.x}; no rebuild is required. The report
lists the integrator total, the Coulomb force, the equation-of-motion
evaluation, the Runge--Kutta update, the bead topology operations (add,
remove and erase bead, breakup check), statistics, scheduled output, and
restart output. The Coulomb, equation-of-motion and Runge--Kutta regions are
nested within the integrator total, and their values must not be added to
it. The equation-of-motion and Runge--Kutta regions are instrumented only in
the CPU code of the Euler, RK2 and RK4 integrators
(\texttt{integrator\_mod.f90}); the OpenACC device step has no such regions,
so a run that takes it, as Test Case 9 does from its first step, reports
zero for them and, within the integrator, times only the Coulomb region. The
equation-of-motion and Runge--Kutta times quoted below were measured with
the accelerator paths of the porting milestones, which ran inside those
integrators.

The report is written only to the terminal and gives cumulative wall time,
percentage of the complete temporal loop, and call count for each explicitly
instrumented region. It is not an automatic profile of every Fortran
subroutine. The fourth-order Runge--Kutta integration used by this test makes
four Coulomb evaluations per step, yielding 4,000 calls. Clock reads add a
small overhead, so profiling must have the same enabled or disabled state in
both runs being compared. In MPI execution, the detailed table is local to
rank zero rather than a maximum over ranks; the synchronized complete-loop
timer remains the appropriate MPI scaling measurement.

In an initial profiled run, the NVFORTRAN CPU loop required 39.813621 s,
of which 38.232985 s (96.03\%) was spent in 4,000 Coulomb evaluations.
The A30 loop required 3.320607 s, with 2.164045 s (65.17\%) in the same
Coulomb region. The corresponding speedups were approximately 11.99 for the
complete loop and 17.67 for Coulomb alone. Repeating this profile after each
porting milestone provides a direct view of time moving from the Coulomb
kernel to remaining host work, device transfers, or other force terms.

The complete sampled CPU and A30 OpenACC numerical outputs are versioned in
\texttt{tests/performance/test9/} (regenerated on 7 October 2026 for the
collector rule; CPU and A30 records identical). The accompanying comparison script checks
later CPU and GPU results with relative tolerance $10^{-6}$ and absolute
tolerance $10^{-9}$. These records remain outside the automatic regression
matrix because of the benchmark's longer execution time.

The development targets \texttt{nvfortran-openacc-force-oracle} and
\texttt{nvfortran-openacc-coulomb-oracle} also cover this non-evaporative RK4
case. The first evaluates all four trusted host force stages and uploads their
derivatives; the second evaluates only the four direct Coulomb sums on the
host. Against the versioned NVFORTRAN CPU output, the standard GPU path,
complete-force oracle, and Coulomb-only oracle produced worst normalized
differences of $7.97\,10^{-5}$, $3.00\,10^{-7}$, and $8.52\,10^{-5}$,
respectively. Thus Coulomb accumulation order is not the dominant Test Case 9
RK4 difference. Oracle builds are not performance configurations.

A subsequent profiler refinement measured 2.026551 s (56.28\%) in Coulomb,
1.420609 s (39.45\%) in the equation-of-motion evaluations, and 0.014712 s
(0.41\%) in the separate Runge--Kutta vector updates on the A30. Each
equation-of-motion and Coulomb region was called 4,000 times. This breakdown
selected the three-dimensional equation-of-motion chain as the next meaningful
accelerator target; porting the vector updates alone could not materially improve
this workload. The trajectory still matched the versioned A30 reference
exactly at the saved output precision.

The following paragraphs record the porting milestones of August 2026,
which the common device step of version 2.0 has superseded; their normalized
differences refer to the records of that time. The first
equation-of-motion offload milestone used one explicit OpenACC
kernel per RK4 stage for the Test 9 force assembly. The local three-point
curvature construction also executed entirely on the device: every bead read
only itself and its two neighbours, and no curvature array was transferred from
the host. Because the initially straight jet makes the circumcentre arithmetic
sensitive to floating-point contraction, the OpenACC target uses the
NVFORTRAN \texttt{nofma} GPU option. In an updated paired measurement built
from the same source with NVFORTRAN 24.3, the CPU and A30 complete-loop times
were 38.616119 s and 3.159748 s, respectively, for a speedup of 12.22. The
CPU/A30 regional times were 37.059132/2.250507 s for Coulomb (16.47 speedup),
1.398234/0.736914 s for equation-of-motion evaluation including curvature
(1.90 speedup), and 0.018556/0.030343 s for the Runge--Kutta updates. Coulomb
and equation-of-motion evaluation each had 4,000 calls. The slower device-side
RK updates represented less than one percent of the A30 loop. The complete
saved trajectory passed the
A30 baseline comparison with relative tolerance $10^{-6}$ and absolute
tolerance $10^{-9}$; the worst normalized difference was $7.82\,10^{-5}$.
That first EOM milestone used call-scoped transfers and was restricted to the fixed Test 9
configuration; other configurations retained the CPU path.

The subsequent persistent-data milestone mapped the complete Test 9 state,
Coulomb force, equation-of-motion derivatives, and Runge--Kutta scratch arrays
once and retained them on the A30 across timesteps. Cross sections and all four
Runge--Kutta updates were computed on the device, and the Coulomb result was
consumed directly by the equation-of-motion kernel. The CPU statistics of
that time still required one update of the seven primary state arrays after
each timestep, corresponding to 56,056 bytes per step for the 1,001 array
entries (indices 0 to 1,000) of the 1,000-bead jet.

In a representative profiled run, the persistent complete loop took 2.451978
s, compared with 3.159748 s for the call-scoped A30 implementation and
38.616119 s for the paired NVFORTRAN CPU run. The persistent Coulomb,
equation-of-motion, and Runge--Kutta regions took 2.006970 s, 0.112892 s, and
0.191860 s, respectively. The Runge--Kutta region included the once-per-step
full-state update to the host. The complete-loop speedup over the CPU was
15.75. The trajectory passed the unchanged A30 baseline with relative
tolerance $10^{-6}$ and absolute tolerance $10^{-9}$; its worst normalized
difference was $7.8\,10^{-5}$.

In the following device-resident-statistics milestone, the path length and
maximum stress were accumulated on the accelerator after each step. Their
scalar counters remained on the device. The complete primary state was copied to
the host only at the five scheduled 200-step samples. The final restart recorded
the last synchronized timestep and reused the step-1000 host snapshot rather
than downloading it again. Thus only five full-state synchronization events
remained. A representative A30 run took
2.468580 s for the complete loop, of which 0.056676 s was attributed to the
small statistic kernels. The trajectory passed the unchanged A30 baseline
with relative tolerance $10^{-6}$ and absolute tolerance $10^{-9}$; the worst
normalized difference was $7.97\,10^{-5}$.

The next milestone fused the path-length and maximum-stress reductions with
the final Runge--Kutta state update. Each device thread reconstructed the
updated position of the next bead from the same Runge--Kutta coefficients,
avoiding a neighbour race. Two small follow-up kernels preserved the rule that
the last bead index wins when maximum stresses are equal. In a representative
A30 run, the statistics region decreased from 0.056676 s to 0.036373 s, and
the complete loop took 2.457896 s. An extended comparison matched maximum
stress and its position exactly; path length differed by at most
$2\,10^{-8}$ cm because of reduction ordering.

In the selective-output milestone, ordinary statistical output began to
download only the seven state values of the selected bead and four scalar
accumulators, as the device step of version 2.0 still does. The
sampling interval is computed from \texttt{print time / timestep}; the value
of 200 steps belongs to the standard Test 9 input and is not hardcoded. OpenACC
transfer tracing reported 280 bytes for the five point samples, 140 bytes for
their statistics, and one 56,056-byte complete-state download for the final
restart, or 56,476 bytes in total. XYZ, PDB, binary trajectory, and periodic
restart output still request a complete snapshot at their configured cadence.
